# SP-003 Process Foundation Standard

## 1. Purpose and authority

This standard defines the Process Foundation of the Canonical Computing
Architecture (CCA).

The Process Foundation provides deterministic, synchronous execution of
`RepresentationDocument` objects. It converts valid passive Representation
state into an immutable `ProcessDefinition`, executes that definition through
an isolated `ExecutionContext`, and returns an `ExecutionResult`.

CCA-PROC-1.0 intentionally defines the smallest executable profile that can be
derived from an arbitrary CCA-REP-1.0 document without inventing an executable
type taxonomy. Execution in this version is deterministic structural
visitation. It produces an ordered identity trace and has no external side
effects.

The terms **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
express requirement strength. `MUST` and `MUST NOT` define conditions for
CCA-PROC-1.0 conformance.

The package authority order is:

```text
API-002-HPP
    -> API-002
    -> SP-003
    -> CCA-PROC requirements
    -> IS-005
```

`API-002-HPP` is the sole authority for public C++ declarations. `API-002` is
the authority for public API behavior. This document is the authority for the
Process Foundation architecture. The requirement registry makes obligations
individually traceable. IS-005 constrains implementation without redefining
the higher authorities.

The conformance document defines assessment and evidence expectations. It does
not add behavior.

## 2. Scope

CCA-PROC-1.0 defines:

- `ProcessDefinition`;
- `ExecutionContext`;
- `ExecutionState`;
- `ExecutionResult`;
- the `ProcessEngine` public service;
- admissibility of `RepresentationDocument` inputs;
- deterministic definition materialization;
- deterministic structural execution order;
- execution state transitions;
- result and diagnostic behavior;
- ownership, lifetime, exception-safety, and thread-safety rules;
- Runtime Foundation service integration; and
- conformance evidence for IM-005.

CCA-PROC-1.0 does not define a process language. In particular, it assigns no
action, condition, branch, dependency, entry-point, or control-flow meaning to
Representation type names, properties, relationships, or metadata.

## 3. Architectural context

Process is a Layer 4 Domain Engine under CCA-RF-1.0. Representation and
Process are peer Domain Engines. Process consumes the public CCA-REP-1.0
contract and depends downward on the Layer 3 Runtime Foundation.

The platform processing flow is:

```text
Compiler
   |
   v
RepresentationDocument
   |
   v
Process Foundation
   |
   v
Runtime Foundation
```

This flow describes production, consumption, and dependency. It does not
replace or renumber the canonical five-layer model in CCA-RF-1.0. The Compiler
produces Representation data; the Process Foundation consumes that data; and
Runtime-hosted Process operation depends on the Runtime Foundation.

The Process Foundation:

- MUST NOT become a seventh Runtime Foundation component;
- MUST NOT cause the Runtime Foundation to depend upward on Process;
- MUST NOT place execution behavior inside Representation objects;
- MUST NOT take ownership of a caller's `RepresentationDocument`; and
- MUST NOT redefine the Compiler, Representation, or Runtime contracts.

## 4. Design principles

### SP-003-P1 — Deterministic execution

Equivalent valid Representation semantic state and equivalent initial
Process execution state MUST produce equivalent definitions, state
transitions, traces, results, and diagnostics.

### SP-003-P2 — Passive input

Process execution MUST observe Representation state without modifying,
freezing, removing, or adding semantic objects.

### SP-003-P3 — Explicit execution state

Every execution MUST use an isolated `ExecutionContext` and the exact
CCA-PROC-1.0 execution state model.

### SP-003-P4 — Runtime-hosted service

Within a Runtime instance, `ProcessEngine` MUST be exposed as one typed Service
Contract with `ExactlyOne` cardinality and an internal Provider.

### SP-003-P5 — No hidden semantics

Process execution MUST NOT derive actions or control flow from unspecified
Representation type names, property names, values, metadata, or relationship
types.

### SP-003-P6 — No hidden environment

Process outcomes MUST NOT depend on mutable global state, wall-clock time,
randomness, environment variables, filesystem state, network state, or
process scheduling.

## 5. Public concepts

### 5.1 ProcessDefinition

A `ProcessDefinition` is an immutable, owned execution plan materialized from
one valid `RepresentationDocument` state.

It contains:

- the canonical ordered sequence of copied Representation identifiers;
- the number of entities in the source state;
- the number of relationships in the source state; and
- the total number of entity-owned and relationship-owned properties.

A definition owns its execution plan. It does not retain the source document
or references, pointers, views, or iterators into that document.

### 5.2 ExecutionContext

An `ExecutionContext` is the mutable state of exactly one attempted execution
of one `ProcessDefinition`.

It owns:

- a value copy of the definition;
- the current `ExecutionState`; and
- the ordered trace produced by the execution.

The Process `ExecutionContext` is distinct from the Runtime Foundation's
instance execution context. It neither owns a Runtime instance nor advances
Runtime lifecycle state.

### 5.3 ExecutionState

CCA-PROC-1.0 defines exactly these public execution states:

```text
Ready
Running
Completed
Failed
```

`Ready` and `Running` are non-terminal. `Completed` and `Failed` are terminal.
No paused, scheduled, waiting, cancelled, retrying, or distributed state is
defined.

### 5.4 ExecutionResult

An `ExecutionResult` is the owned, terminal outcome of one `ProcessEngine`
execution request.

It exposes:

- terminal execution state;
- strongly typed result code;
- success predicate;
- deterministic message;
- ordered execution trace; and
- Representation validation diagnostics when the input is invalid.

### 5.5 ProcessEngine

`ProcessEngine` is the only public Process Foundation service.

It is a stateless, default-constructible facade that:

- validates direct document inputs;
- materializes definitions;
- creates or accepts execution contexts;
- enforces the execution state machine;
- performs deterministic structural visitation; and
- returns terminal execution results.

## 6. Representation input contract

The input to direct execution is:

```cpp
const cca::representation::RepresentationDocument&
```

The Process Foundation MUST use only the public CCA-REP-1.0 API.

Before a document is materialized or executed, the Process Foundation MUST
perform read-only validation using CCA-REP-1.0 validation behavior. It MUST
preserve the returned diagnostic order.

Mutable, internally Validated, and Frozen documents are admissible when their
currently observable semantic state is valid. Process does not need to
distinguish Mutable from Validated, because CCA-REP-1.0 does not expose that
distinction publicly.

The Process Foundation:

- MUST NOT freeze the input;
- MUST NOT change its Representation lifecycle;
- MUST NOT start a Representation transaction;
- MUST NOT commit or roll back a Representation transaction; and
- MUST NOT retain input references after definition materialization completes.

A valid empty `RepresentationDocument` is a valid Process input. Its
definition and successful execution trace are empty.

An active Representation transaction is not independently observable through
the CCA-REP-1.0 public API. A valid state observed during such a transaction
MAY be materialized. The resulting definition remains independent of later
commit or rollback.

The caller MUST prevent concurrent mutation of the source document during
validation and materialization.

## 7. ProcessDefinition materialization

Materialization first validates the input. If construction through the public
`ProcessDefinition` constructor receives an invalid document, construction
MUST fail with `std::invalid_argument` and create no definition.

For a valid document, materialization copies the canonical execution sequence
and counts defined in Section 8. Once construction completes:

- later source mutation MUST NOT change the definition;
- later source rollback MUST NOT change the definition;
- source destruction MUST NOT invalidate the definition; and
- copied identifiers MUST retain their exact CCA-REP-1.0 values.

Representation metadata is descriptive and non-semantic under CCA-REP-1.0.
It MUST NOT change definition contents, execution order, or results.

Representation types, property names, property values, relationship
direction, and relationship types MUST NOT be interpreted as actions,
conditions, dependencies, branches, or control-flow instructions in
CCA-PROC-1.0.

## 8. Deterministic execution profile

CCA-PROC-1.0 execution is structural visitation. It does not invoke user code
or perform an external effect.

The canonical execution sequence is:

1. Visit entities in `RepresentationDocument::entities()` order.
2. Immediately after each entity, visit that entity's properties in
   `RepresentationEntity::properties()` order.
3. After all entities and entity properties, visit relationships in
   `RepresentationDocument::relationships()` order.
4. Immediately after each relationship, visit that relationship's properties
   in `RepresentationRelationship::properties()` order.

Visiting an identity-bearing object appends one owning copy of its
`RepresentationId` to the execution trace.

The document root and metadata have no identifier and add no trace entry.
Relationship endpoints are already represented by entity entries. They do not
add duplicate trace entries and do not reorder execution.

Relationship direction remains Representation semantic state, but it does not
define execution precedence or dependency in CCA-PROC-1.0. Cycles,
self-relationships, disconnected components, and insertion order therefore
require no scheduling algorithm.

Successful execution MUST visit every identifier in the definition exactly
once and in canonical order. The completed trace MUST equal
`ProcessDefinition::executionOrder()`.

This profile is intentionally side-effect-free. Adding executable actions,
callbacks, conditions, branching, retries, or control-flow semantics requires
a future governed specification revision.

## 9. Execution lifecycle

Constructing an `ExecutionContext` establishes `Ready`.

Executing a Ready context follows exactly:

```text
Ready -> Running -> Completed
```

The engine MUST finish material needed for the result before making a
transition that cannot be rolled back under the strong exception guarantee.

An operation-level failure represented by an `ExecutionResult` uses terminal
`Failed`. Invalid direct Representation input produces a Failed result without
creating a caller-visible context.

An `ExecutionContext` is one-shot. Calling `execute(context)` when its state is
not `Ready` MUST throw `std::logic_error` and MUST leave the context unchanged.

Execution state changes do not change Runtime lifecycle state. Process
`Failed` is not Runtime `Failed`.

## 10. ExecutionResult contract

CCA-PROC-1.0 defines these result codes:

| Code | State | Meaning |
|---|---|---|
| `Success` | `Completed` | The complete definition was visited |
| `InvalidRepresentation` | `Failed` | CCA-REP-1.0 validation rejected the direct input |

`ExecutionResult::succeeded()` MUST be true exactly for
`Completed`/`Success`.

A successful result MUST contain:

- `ExecutionState::Completed`;
- `ExecutionResult::Code::Success`;
- an empty message;
- no validation diagnostics; and
- the complete canonical execution trace.

An invalid-input result MUST contain:

- `ExecutionState::Failed`;
- `ExecutionResult::Code::InvalidRepresentation`;
- a deterministic non-empty message;
- the complete ordered CCA-REP-1.0 validation diagnostics; and
- an empty execution trace.

Diagnostic message wording is not a source-compatibility contract. Result
codes, state mappings, and ordering are compatibility contracts.

## 11. ProcessEngine behavior

`ProcessEngine` provides three equivalent entry surfaces:

```cpp
execute(const RepresentationDocument&)
execute(const ProcessDefinition&)
execute(ExecutionContext&)
```

Direct document execution MUST:

1. validate the document;
2. return `InvalidRepresentation` if validation fails;
3. materialize a definition when validation succeeds;
4. create a Ready context; and
5. execute that context.

Definition execution MUST create a Ready context and execute it.

Context execution MUST enforce Section 9 and produce the trace in Section 8.

For the same valid document state, these calls MUST produce equivalent
terminal results:

```cpp
engine.execute(document)
engine.execute(ProcessDefinition{document})
```

For the same definition, these calls MUST produce equivalent terminal results:

```cpp
engine.execute(definition)

ExecutionContext context{definition};
engine.execute(context)
```

Execution is synchronous. `execute` returns only after reaching a terminal
Process execution state or before propagating a documented standard exception.

The required direct public example is:

```cpp
using cca::process::ExecutionResult;
using cca::process::ProcessEngine;
using cca::representation::RepresentationDocument;

RepresentationDocument model;

ProcessEngine engine;

ExecutionResult result = engine.execute(model);
```

The default empty document is valid and therefore returns a successful
Completed result with an empty trace.

## 12. Runtime Foundation integration

Direct construction supports embedding, examples, and unit testing. A complete
CCA-PROC-1.0 implementation MUST additionally integrate `ProcessEngine` with a
CCA-RF-1.0 Runtime instance.

Within each hosting Runtime instance:

- `ProcessEngine` MUST be a typed Service Contract;
- its cardinality MUST be `ExactlyOne`;
- its Provider MUST remain internal to Runtime composition;
- the Provider MUST participate in the validated Runtime dependency graph;
- the Provider MUST start and stop under Runtime lifecycle control;
- consumers MUST resolve the contract through the instance Service Registry;
- calls MUST occur only after that Runtime reaches `Running`; and
- Process outcomes MUST remain isolated to that Runtime instance.

Runtime Freeze freezes service composition. It does not freeze per-call
`ExecutionContext` operational state.

Process execution MUST NOT:

- register or replace Runtime services after Runtime Freeze;
- advance or invent Runtime lifecycle transitions;
- resolve services by string;
- access a Provider from another Runtime instance; or
- rely on a process-wide singleton.

Any required Runtime collaborator introduced by a conforming implementation
MUST be declared as a typed Service Contract and supplied through Dependency
Injector. CCA-PROC-1.0 defines no public Process Event Bus event type and does
not make successful execution dependent on asynchronous event delivery.

A Process input rejection is an `ExecutionResult`; it is not a Runtime
lifecycle failure. Provider start or stop failure remains a CCA-RF-1.0 Runtime
failure and follows the Runtime failure path rather than being converted into
an `ExecutionResult`.

## 13. Determinism

Equivalent inputs mean equivalent:

- validated Representation identifiers and insertion order;
- entity, relationship, and property counts;
- initial Process execution state; and
- Process API operation.

Equivalent inputs MUST produce equivalent:

- acceptance or rejection;
- definition execution order and counts;
- Process state transitions;
- result state and code;
- trace identifiers and order; and
- validation diagnostic code, severity, message, and order.

Determinism MUST NOT depend on object addresses or allocation layout.

## 14. Ownership and lifetime

The caller owns the source `RepresentationDocument`.

`ProcessDefinition` owns copied identifiers and counts. It is a regular value
type and is copyable and movable.

`ExecutionContext` exclusively owns its definition value, state, and trace. It
is neither copyable nor movable so one execution identity cannot be duplicated
or transferred during a run.

`ExecutionResult` owns its message, trace, and diagnostic values. It is
copyable and movable.

References and views returned by Process accessors remain valid until the
supplying object is assigned, mutated where permitted, moved from, or
destroyed. Executing a context may invalidate iterators and element references
into its previously observed trace, but not a reference to the trace
collection object itself.

## 15. Failure and exception safety

Public Process operations expose only standard C++ exceptions.

| Condition | Outcome |
|---|---|
| Invalid document passed to `ProcessEngine::execute(document)` | Failed `InvalidRepresentation` result |
| Invalid document passed to `ProcessDefinition` construction | `std::invalid_argument` |
| Non-Ready context passed to `ProcessEngine::execute(context)` | `std::logic_error` |
| Standard-library allocation failure | May propagate |

Validation failure is an expected domain outcome for direct execution and MUST
NOT be reported by an implementation-specific exception.

Definition construction and all execute overloads MUST provide the strong
exception guarantee. If an exception propagates:

- the source document is unchanged;
- an existing definition is unchanged;
- an existing execution context is unchanged; and
- no partial result is returned.

## 16. Thread safety

`ProcessEngine` has no mutable execution state. Distinct calls on the same
engine MAY execute concurrently when they use distinct documents or externally
synchronized document access and distinct contexts.

Completed `ProcessDefinition` and `ExecutionResult` values support concurrent
const access.

One `ExecutionContext` MUST NOT be accessed concurrently without external
synchronization.

CCA-REP-1.0 provides no general concurrent document-access guarantee. The
caller MUST externally synchronize validation and materialization against all
access that may conflict under the CCA-REP-1.0 contract.

Runtime-hosted execution additionally follows the thread-safety contract of
the hosting Runtime instance.

## 17. Explicit exclusions

CCA-PROC-1.0 MUST NOT introduce:

- scheduling;
- persistence;
- serialization;
- networking;
- distributed execution;
- BPMN;
- workflow-engine behavior;
- MemoryOS;
- Studio or graphical user interfaces;
- Artificial Intelligence;
- plugins;
- user-defined actions or callbacks;
- process event schemas;
- cancellation, pause, resume, retry, or timeout semantics; or
- code generation.

## 18. Implementation constraints

Implementations MUST:

- use modern C++;
- match API-002-HPP exactly;
- preserve API-002 behavior;
- keep internal Providers out of the public Process API;
- preserve Runtime instance isolation;
- preserve deterministic ordering;
- avoid global mutable state and circular dependencies;
- compile warning-free with warnings treated as errors; and
- provide automated tests for every mandatory requirement and every normative
  public API behavior.

Internal storage, indexing, materialization helpers, allocation strategy, and
visitation algorithms remain implementation-defined.

## 19. Conformance

A conforming CCA-PROC-1.0 implementation MUST:

- implement all five public concepts;
- expose only `ProcessEngine` as the public Process service;
- satisfy every required item in `requirements.yaml`;
- match API-002-HPP declarations and API-002 behavior;
- implement the deterministic structural execution profile;
- integrate ProcessEngine as an ExactlyOne Runtime Service Contract with an
  internal Provider;
- preserve all exclusions;
- pass the complete automated conformance suite; and
- build warning-free with warnings treated as errors.

Partial implementation of the state model, direct API, or Runtime integration
is not CCA-PROC-1.0 conformance.
