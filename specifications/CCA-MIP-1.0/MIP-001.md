## 1. Purpose

This specification defines the canonical Memory Investigation Package. A
Memory Investigation Package is an immutable, portable representation of
observed MemoryOS cognition and any deterministic investigations derived from
that observation. The package is the interchange contract for future SDKs,
Studio, command-line tools, network interfaces, plugins, and connectors.

The package records cognition, not presentation. It preserves authoritative
observations and reference-only investigations so a conforming consumer can
validate and reconstruct them without consulting a renderer or live Runtime.

## 2. Scope

### 2.1 In scope

MIP-001 specifies:

- the `.mip` physical representation and logical package layout;
- manifest and technical metadata;
- Observation, Cognitive Trace, Cognitive Replay, Cognitive Evolution, and
  Comparative Reconstruction records;
- verification evidence and cryptographic checksums;
- canonical serialization, identifier, ordering, and hash rules;
- validation, import, export, and atomic failure behavior;
- format versioning, compatibility, unknown sections, and extensions; and
- conformance examples and validation evidence.

### 2.2 Out of scope

MIP-001 does not define a programming-language API, transport protocol,
storage Provider, user interface, renderer, execution model, compression,
encryption, digital-signature system, or authentication scheme. It does not
change MemoryOS Runtime behavior or any MemoryOS 1.0 or 1.1 capability.

An out-of-scope concern is not authorized merely because a `.mip` producer or
consumer could implement it outside the package.

## 3. Normative language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**,
and **MAY** are normative. A conforming producer, consumer, or verifier meets
all applicable mandatory requirements in [requirements.yaml](requirements.yaml).

When prose and the JSON Schema differ, the prose is authoritative for semantic,
ordering, derivation, integrity, compatibility, and prohibited-content rules.
The schema is authoritative only for the machine-checkable structural subset
that it expresses.

## 4. Terms and definitions

| Term | Definition |
|---|---|
| Memory Investigation Package | One immutable `.mip` document containing cognition from exactly one Workspace. |
| Producer | A component that exports canonical `.mip` bytes. |
| Consumer | A component that imports or otherwise reads `.mip` bytes. |
| Verifier | A component that validates `.mip` structure, integrity, references, and deterministic derivations. |
| Observation | A detached, accepted snapshot of authoritative cognition at one source-defined sequence position. |
| Semantic record | One observed cognitive value and its authoritative semantic revision. |
| Typed reference | A portable identity tuple of `kind`, exact `identifier`, and deterministic `occurrence`. |
| Cognitive Trace | An ordered, immutable, reference-only journey from evidence to an observed Reflection. |
| Cognitive Replay | A deterministic, reference-only construction order derived from one Cognitive Trace. |
| Cognitive Evolution | A deterministic semantic difference set between two Observations. |
| Comparative Reconstruction | A deterministic alignment of two Cognitive Traces that identifies exact divergence. |
| Canonical bytes | The unique UTF-8 JSON byte sequence produced by RFC 8785 for a valid package value. |
| Core section | A named top-level MIP section defined by this specification. |
| Extension section | A namespaced entry inside `extensions`; it is never a new core field. |
| Critical extension | An extension that a Consumer must understand before it can safely use the package. |
| Cognition digest | The SHA-256 commitment to the five semantic artifact sections only. |
| Package digest | The SHA-256 commitment to the header and every core section except `integrity`. |

## 5. Architectural boundary

### 5.1 Authority and ownership

An Observation is the sole owner of semantic payload inside a package. Traces,
Replays, Evolutions, and Comparative Reconstructions contain typed references,
revision digests, order, and classifications only. They **MUST NOT** duplicate
Observation payload.

One package belongs to exactly one Workspace. The `workspaceIdentifier` in the
manifest, every Observation, and every derived artifact **MUST** match exactly.
No package operation transfers Workspace ownership.

```text
MemoryOS source truth
        |
        v
accepted detached Observation  <---- sole semantic payload owner
        |          |      |
        v          |      v
reference-only     |   semantic difference
Cognitive Trace    |   between Observations
        |          |      |
        v          |      v
reference-only     +-> Comparative Reconstruction
Cognitive Replay       (reference-only alignment)
```

The complete dependency diagram is in
[package-layout.mmd](diagrams/package-layout.mmd).

### 5.2 Runtime and presentation independence

A package is complete without a running MemoryOS Runtime, Studio, renderer, or
Provider. Importing or verifying a package **MUST NOT** require any of them.
Presentation is derived after import and is not package cognition.

### 5.3 Immutability

A `.mip` file is immutable. Any semantic, metadata, extension, or verification
change produces new canonical bytes and a new package digest. A Consumer may
materialize mutable private objects, but that does not alter the imported
package or its identity.

## 6. Physical representation

### 6.1 Single canonical document

A `.mip` file **MUST** be one UTF-8 JSON document serialized exactly according
to RFC 8785, JSON Canonicalization Scheme (JCS). It **MUST NOT** be a ZIP,
directory, multipart body, database, or container of sidecar files.

The file:

- has extension `.mip`;
- uses media type `application/vnd.memoryos.mip+json`;
- contains no byte-order mark;
- contains exactly one JSON value;
- contains no duplicate object member names; and
- is byte-for-byte equal to the JCS serialization of its parsed value.

A Consumer **MUST** reject noncanonical bytes. It **MUST NOT** silently parse,
normalize, and accept them as a canonical package.

### 6.2 JSON value restrictions

Values are limited to JSON objects, arrays, strings, booleans, null, and finite
numbers accepted by RFC 8785. `NaN`, positive or negative infinity, negative
zero, comments, trailing commas, duplicate member names, and invalid Unicode
are invalid. Integers outside the interoperable range
`[-9007199254740991, 9007199254740991]` **MUST** be encoded as decimal strings
under a field whose contract declares that representation.

Strings, including identifiers, **MUST NOT** be trimmed, case-folded, locale
transformed, or Unicode-normalized during import, export, comparison, or hash
calculation.

## 7. Package layout

### 7.1 Required top-level members

Every package contains exactly these top-level members:

| Member | Cardinality | Purpose |
|---|---:|---|
| `$schema` | 1 | Exact schema identifier `urn:memoryos:mip:schema:1.0.0`. |
| `kind` | 1 | Exact value `MemoryInvestigationPackage`. |
| `formatVersion` | 1 | Semantic wire-format version with major version `1`; this publication defines `1.0.0`. |
| `manifest` | 1 | Identity, Workspace, profiles, features, and inventory. |
| `metadata` | 1 | Technical provenance only. |
| `observations` | 1..n | Authoritative cognitive payload. |
| `traces` | 0..n | Reference-only Cognitive Traces. |
| `replays` | 0..n | Deterministic Replay plans. |
| `evolutions` | 0..n | Semantic differences between Observations. |
| `comparativeReconstructions` | 0..n | Deterministic two-trace alignments. |
| `extensions` | 0..n entries | Namespaced optional or critical extension sections. |
| `verification` | 1 | Export-time conformance evidence. |
| `integrity` | 1 | Section, cognition, and package digests. |

All array-valued core sections are present even when empty. This eliminates
absent-versus-empty ambiguity. Unknown top-level members and unknown members
inside closed core records are invalid. Future data belongs only in
`extensions`.

A Producer claiming conformance with wire format `1.0.0` emits that exact
`formatVersion`. A Consumer applies the same-major compatibility rules in
section 20 before selecting the major-version core schema; this is why the
major-1 schema accepts later stable `1.MINOR.PATCH` values.

An Observation-only package is valid. A producer **MUST NOT** manufacture a
Trace, Replay, Evolution, or Comparative Reconstruction merely to populate an
otherwise empty section.

### 7.2 Manifest

`manifest` contains:

- `packageIdentifier`: a nonempty, stable identifier supplied explicitly to
  the Producer;
- `workspaceIdentifier`: the exact Workspace identifier shared by the package;
- `profiles`: exact canonicalization (`RFC8785`), digest (`SHA-256`), and
  validation (`MIP-CORE-1.0`) profiles;
- `features.required`: understood features required to consume the package;
- `features.optional`: noncritical features that may be ignored while retained;
  and
- `inventory`: exact counts for all five artifact arrays.

The inventory is derived metadata. A mismatch between inventory and section
cardinality is invalid. A Producer **MUST NOT** replace, regenerate, or
implicitly synthesize `packageIdentifier`; it is an exact export input.

### 7.3 Metadata

`metadata` contains only technical provenance:

- the Producer name and version;
- the source product name and version; and
- an optional `exportedAt` value supplied explicitly by the caller and encoded
  as RFC 3339 UTC with a `Z` suffix.

Export time **MUST NOT** be read implicitly from a clock. Omitting `exportedAt`
is the deterministic default. Metadata **MUST NOT** contain marketing copy,
display titles, screenshots, generated descriptions, summaries, explanations,
or presentation preferences.

### 7.4 Extensions

`extensions` is a JSON object keyed by globally unique reverse-DNS names. Each
entry contains an extension `version`, a Boolean `critical`
flag, and canonical JSON `payload`.

An extension **MUST NOT**:

- override, reinterpret, or replace a core member;
- change core identity, ordering, validation, or derivation rules;
- duplicate semantic payload already owned by an Observation;
- introduce executable behavior or opaque binary content; or
- evade any prohibited-content rule in section 15.

Unknown noncritical extensions are ignored semantically and preserved exactly
on round-trip. Unknown critical extensions cause atomic rejection. An exporter
that cannot preserve an unknown noncritical extension **MUST** fail rather than
silently remove or rewrite it.

The feature arrays and extension entries are a bijection. They are disjoint:
every `critical: true` extension key appears exactly once in
`features.required`, every `critical: false` key appears exactly once in
`features.optional`, and neither feature array contains a name absent from
`extensions`.

## 8. Portable identity and references

### 8.1 Typed reference

Every semantic record and relationship has a typed reference:

```json
{"kind":"memoryos.longTermMemoryEntry","identifier":"ltm-001","occurrence":0}
```

The identity tuple is:

1. `kind`: a stable qualified semantic type;
2. `identifier`: the exact source identifier; and
3. `occurrence`: a zero-based disambiguator among values with equal `kind` and
   `identifier` in the same authoritative source order.

The source identifier is preserved exactly and is never replaced with a newly
created identifier. `occurrence` does not alter source identity; it only makes
otherwise colliding observations addressable. Producers assign occurrences
contiguously in authoritative source order and preserve them in every package
reference.

Typed references are compared as exact JSON scalar tuples. Private Studio
world keys, array paths, DOM identifiers, and renderer addresses are not
portable references and **MUST NOT** appear as core identity.

### 8.2 Uniqueness and closure

Within one Observation, record references are unique and relationship
references are unique. Observation identifiers are unique across
`observations`; identifiers are also unique within each of `traces`, `replays`,
`evolutions`, and `comparativeReconstructions`. Every relationship endpoint
resolves to a record in that Observation. Every reference in a derived artifact
resolves in its bound Observation or, for a two-observation artifact, in the
explicitly named side. Ambiguous, missing, duplicate, or cross-Workspace
references invalidate the whole package.

## 9. Observation

### 9.1 Record shape

An Observation contains:

- `identifier`: exact source Observation identity;
- `sequence`: source-defined nonnegative ordering value;
- `workspaceIdentifier`;
- `records`: semantic records; and
- `relationships`: semantic relationships.

Each semantic record contains a typed `reference`, one `role`, an ordered
`provenance` array, and an authoritative `revision` object. A provenance entry
contains exact typed `source` and `relationship` references. The named
relationship must connect that source record to the record that owns the
provenance entry; stored relationship direction may be forward or reverse.

Core roles are:

- `evidence`;
- `semanticTransformation`;
- `retrieval`;
- `reflection`; and
- `context` for observed cognition that is not classified as one of the four
  investigation roles.

Each relationship contains a typed `reference`, a stable
`relationshipType`, typed `from` and `to` endpoints, and its authoritative
semantic `revision` object.

Provenance follows this closed grammar:

- `evidence` and `context` records have an empty provenance array;
- `semanticTransformation` has one or more ordered `evidence` sources;
- `retrieval` has exactly one `semanticTransformation` source; and
- `reflection` has one or more ordered `retrieval` sources.

Every provenance relationship is unique within the Observation, every source
and relationship resolves exactly, and the provenance graph is acyclic.
Provenance arrays preserve authoritative source order and are never sorted by
the serializer.

The revision object contains source cognition required to reconstruct the
Observation. It **MUST NOT** contain layout, view, control, cache, or Runtime
implementation data. Legitimate source-authored cognitive text may be present;
AI- or LLM-generated explanation text introduced by the exporter may not.

### 9.2 Observation acceptance

Only a coherent, successful, detached source observation may be exported. A
failed or partially acquired source result is not an Observation. The package
does not store the observing query, transient operation result, active route,
or highlight delta.

Observation sequences preserve source chronology. A package may contain a
subset and therefore sequence gaps are valid, but sequences must be strictly
increasing after canonical ordering. Duplicate sequence-plus-identifier pairs
are invalid.

### 9.3 Canonical Observation order

`observations` is sorted by numeric `sequence`, then exact
`identifier`. Within each Observation:

- `records` is sorted by reference `kind`, exact `identifier`, then
  `occurrence`;
- `relationships` is sorted by relationship reference using the same tuple;
  and
- arrays inside `revision` retain their authoritative semantic order.

Sorting compares Unicode scalar values exactly as represented; it is not
locale-sensitive and performs no normalization.

## 10. Cognitive Trace

A Cognitive Trace references exactly one included Observation and terminates
at exactly one included record whose role is `reflection`. It contains:

- `identifier`, `observationIdentifier`, and `workspaceIdentifier`;
- a typed `target` reference; and
- one or more ordered branches.

Each branch has a zero-based contiguous `index` and one or more steps. Each
step has a zero-based contiguous `index`, a fixed role, a typed `node`
reference, an optional typed `relationship` reference, and an explicit
traversal `direction`.

The fixed Trace role order is:

1. one or more `originEvidence` steps;
2. exactly one `semanticTransformation` step;
3. exactly one `retrieval` step; and
4. exactly one terminal `reflectionCurrent` step.

Every branch terminates at the Trace target. Only `reflectionCurrent` omits a
relationship and uses null direction. Every other step names a relationship
that touches its node and uses `forward` or `reverse` according to the stored
relationship direction. Branch order preserves authoritative Reflection source
order; evidence steps preserve authoritative provenance order.

Trace and Observation roles correspond exactly:

- `originEvidence` references an `evidence` record;
- `semanticTransformation` references a `semanticTransformation` record;
- `retrieval` references a `retrieval` record; and
- `reflectionCurrent` references the target `reflection` record.

Stage continuity is mandatory. Every origin relationship joins its evidence
node to the branch's transformation node; the transformation relationship
joins that transformation to the branch's Retrieval; and the Retrieval
relationship joins that Retrieval to the target Reflection. Merely touching
the step's own node is insufficient.

A verifier recomputes the complete Trace from the bound Observation as follows:

1. iterate target-Reflection provenance entries in stored order, creating one
   branch for each referenced Retrieval;
2. require that Retrieval's single provenance source to be a
   `semanticTransformation`;
3. emit that transformation's `evidence` provenance entries in stored order as
   `originEvidence` steps;
4. emit the transformation, Retrieval, and target Reflection steps; and
5. resolve each step relationship from the corresponding provenance entry and
   derive `forward` when the stored relationship goes from the step node toward
   the next node, otherwise `reverse`.

The verifier requires exact canonical equality. Stored branch and evidence
order is semantic and is not resorted. Any missing, extra, cyclic, wrongly
typed, or ambiguous provenance link makes Trace reconstruction fail.

## 11. Cognitive Replay

A Replay is an optional immutable construction plan derived from exactly one
included Trace. It contains identifiers, Workspace and Observation binding,
and zero-based contiguous steps. Every step references either one record or one
relationship from the Trace; it never contains semantic payload.

Replay order is derived as follows:

1. iterate roles in `originEvidence`, `semanticTransformation`, `retrieval`,
   `reflectionCurrent` order;
2. for each role, visit branches and steps in stored order;
3. emit each first-seen node once;
4. then emit each first-seen relationship once; and
5. require the final element to be the Trace target.

A Replay node step copies the Trace role, sets its node reference, sets
`relationship` to null, and sets `direction` to null. A Replay relationship
step copies the Trace role and direction, sets its relationship reference, and
sets `node` to null.

The stored Replay **MUST** equal this deterministic projection byte-for-byte
after canonical serialization. Replay status, cursor, completed/current/future
projection, timers, scheduler intervals, Play/Pause state, and camera movement
are presentation or controller state and **MUST NOT** be stored.

## 12. Cognitive Evolution

An Evolution compares exactly two included Observations from the same
Workspace. The `from` Observation must precede the `to` Observation by source
sequence; adjacency is not required. It contains only ordered difference
records and exact revision digests.

The supported difference kinds are:

1. `addedEvidence`
2. `removedEvidence`
3. `addedRelationship`
4. `removedRelationship`
5. `modifiedRelationship`
6. `addedSemanticTransformation`
7. `removedSemanticTransformation`
8. `addedRetrieval`
9. `removedRetrieval`
10. `addedReflection`
11. `removedReflection`

For additions, `beforeRevisionDigest` is null and `afterRevisionDigest` is the
digest of the `to` revision. For removals, the inverse applies. A modified
relationship preserves the same typed relationship identity and supplies two
different revision digests. A changed record revision is represented by one
removal and one addition difference, consistent with its role; each member is
placed independently according to the fixed global kind order above.

Differences are recomputed from authoritative Observation records and sorted
in the fixed kind order above, then by subject `kind`, exact `identifier`, and
`occurrence`. Their `index` values are contiguous after sorting. An Evolution
does not contain summaries, unchanged-record lists, union worlds, layout,
renderer classifications, or pixel differences.

## 13. Comparative Reconstruction

A Comparative Reconstruction references exactly two included, validated
Traces, their two included Observations, and the included Evolution for that
ordered Observation pair. It stores aligned semantic moments only.

The two deterministic Replay sequences are aligned by exact element type and
typed reference using longest common subsequence. When two choices have equal
length, the Observation-A-only element is emitted first. Each contiguous moment
has one state:

- `shared`: same identity, exact revision, Trace role, and direction;
- `aOnly`: element occurs only on the earlier side at this alignment point;
- `bOnly`: element occurs only on the later side at this alignment point; or
- `modified`: same identity with a changed revision or Trace binding.

The only reason codes are `A_ONLY`, `B_ONLY`,
`SEMANTIC_REVISION_CHANGED`, `RELATIONSHIP_REVISION_CHANGED`, and
`TRACE_BINDING_CHANGED`. `divergenceIndices` is the ordered list of moment
indices whose state is not `shared`.

Reason codes use the exact order listed above. State invariants are:

- `shared` has both sides, equal type, reference, revision digest, role, and
  direction, with no reason code;
- `aOnly` has only `from` and exactly `A_ONLY`;
- `bOnly` has only `to` and exactly `B_ONLY`; and
- `modified` has both sides with equal element type and reference, at least one
  changed revision, role, or direction, and the applicable revision code before
  `TRACE_BINDING_CHANGED`.

`SEMANTIC_REVISION_CHANGED` applies only to nodes and
`RELATIONSHIP_REVISION_CHANGED` only to relationships. `A_ONLY` and `B_ONLY`
never appear on a shared or modified moment.

A verifier rebuilds both Replays, alignment, states, reasons, and divergence
indices and requires exact equality. Comparative controller status, cursor,
pause reason, union world, layout, side-by-side render projection, and summary
text are not stored.

## 14. Verification and integrity

### 14.1 Verification section

`verification` contains profile `MIP-CORE-1.0`, status `passed`, and the fixed
ordered checks:

1. `STRUCTURE`
2. `CANONICAL_BYTES`
3. `INTEGRITY`
4. `REFERENCE_CLOSURE`
5. `DETERMINISTIC_DERIVATIONS`
6. `PROHIBITED_CONTENT`

All six statuses are `passed`. This is Producer evidence, not authority. Every
Consumer **MUST** recompute the first five checks and every mechanically
decidable prohibited-content rule, then reject a mismatch. Whether otherwise
valid source cognitive text was authored by the source or added by an exporter
cannot be inferred from package bytes; that part of `PROHIBITED_CONTENT` is a
Producer conformance attestation verified by export tests and review. A package
containing a failed check is not exportable and therefore invalid.

### 14.2 Digest encoding

Every digest is encoded as `sha256:` followed by exactly 64 lowercase
hexadecimal characters. SHA-256 input is the exact UTF-8 byte sequence defined
below. `NUL` means one byte `0x00`.

Semantic revision digests used by Evolution and Comparative Reconstruction
commit to the complete authoritative record rather than payload alone:

```text
recordRevisionDigest = SHA-256(
  UTF8("MIP-1") || NUL || UTF8("record") || NUL || UTF8(JCS(record))
)

relationshipRevisionDigest = SHA-256(
  UTF8("MIP-1") || NUL || UTF8("relationship") || NUL ||
  UTF8(JCS(relationship))
)
```

This binds role, typed identity, endpoints, relationship type, and semantic
revision as applicable. A digest over only the open `revision` object is not a
conforming revision digest.

For every core section except `integrity`:

```text
sectionDigest = SHA-256(
  UTF8("MIP-1") || NUL || UTF8("section") || NUL ||
  UTF8(sectionName) || NUL || UTF8(JCS(sectionValue))
)
```

`integrity.sectionDigests` contains exactly these names in this order:

```text
manifest
metadata
observations
traces
replays
evolutions
comparativeReconstructions
extensions
verification
```

### 14.3 Cognition digest

The cognition digest distinguishes semantic cognition from packaging metadata.
It is computed from the ordered section-digest records for:

```text
observations
traces
replays
evolutions
comparativeReconstructions
```

The commitment value is a JSON array of objects with exactly `name` and
`digest`, in the order above:

```text
cognitionDigest = SHA-256(
  UTF8("MIP-1") || NUL || UTF8("cognition") || NUL ||
  UTF8(JCS(cognitionSectionDigestRecords))
)
```

### 14.4 Package digest

The package commitment object has exact members `$schema`, `kind`,
`formatVersion`, and `sectionDigests`. `sectionDigests` is the complete ordered
list from section 14.2.

```text
packageDigest = SHA-256(
  UTF8("MIP-1") || NUL || UTF8("package") || NUL ||
  UTF8(JCS(packageCommitmentObject))
)
```

The `integrity` section is excluded to avoid self-reference. Every other core
section and every header value is committed. The complete scope is shown in
[integrity-scope.mmd](diagrams/integrity-scope.mmd).

Embedded checksums detect accidental or uncoordinated modification. They do
not establish author identity or authenticity because a party that changes a
package can recompute them. Authenticity requires an externally trusted digest
or a future critical signature extension.

## 15. Prohibited content

The following **MUST NOT** appear anywhere in a package, including metadata,
revisions, verification, and extensions, unless the item is legitimate
source-authored cognitive text expressly allowed below:

- screenshots, thumbnails, images, video, audio, or media payloads;
- HTML, CSS, DOM state, canvas or WebGL buffers, fonts, icons, or themes;
- graph coordinates, layout anchors, camera, zoom, pan, color, animation,
  panel, filter, selected-node, Follow, navigation, inspector, or route state;
- Replay or Comparative cursor, Play/Pause state, timer, scheduler, or autoplay
  state;
- renderer projections, union worlds, highlight lists, display summaries, or
  pixel comparisons;
- AI- or LLM-generated summaries, explanations, rationales, recommendations,
  inferred causality, synthetic events, or fabricated cognition;
- temporary cache, indexes, logs, telemetry, browser storage, history, or
  diagnostics unrelated to conformance;
- Runtime implementation state, pointers, handles, threads, event buses,
  service registries, dependency injectors, or live object references;
- Provider implementation details, credentials, secrets, endpoints, local
  paths, transport configuration, or storage configuration;
- executable scripts, plugins, macros, binaries, native code, or opaque blobs;
  and
- duplicated Observation semantic payload in a derived artifact.

Source-authored cognitive content that was actually present in the accepted
Observation is permitted even when it is textual. This exception never permits
credentials, secrets, executable content, media payloads, Provider
configuration, or presentation/Runtime state. An exporter **MUST NOT** add,
rewrite, summarize, infer, or embellish that content.

## 16. Canonical ordering

Canonical JSON object member order is provided by RFC 8785. Array ordering is
semantic and is fixed separately:

| Collection | Required order |
|---|---|
| Observations | `sequence`, then exact `identifier`. |
| Observation records | typed reference tuple. |
| Observation relationships | typed reference tuple. |
| Record provenance | authoritative stored order; never resorted. |
| Traces | exact `identifier`. |
| Trace branches and steps | stored contiguous `index`; never resorted. |
| Replays | exact `identifier`. |
| Replay steps | stored contiguous `index`. |
| Evolutions | from sequence, to sequence, then exact `identifier`. |
| Evolution differences | fixed difference-kind order, then typed subject reference. |
| Comparative Reconstructions | from sequence, to sequence, from Trace identifier, to Trace identifier, then exact identifier. |
| Comparative moments | stored contiguous `index`; reason codes use the closed order in section 13. |
| Divergence indices | strictly increasing numeric order. |
| Required and optional features | exact Unicode scalar lexical order. |
| Extension keys | RFC 8785 object member order. |
| Verification checks | fixed order in section 14.1. |
| Section digests | fixed order in section 14.2. |

Equivalent semantic input and identical explicitly supplied manifest and
metadata inputs **MUST** produce byte-identical `.mip` output. Ordering **MUST NOT** depend on locale,
wall clock, randomness, hash-map iteration, filesystem order, renderer order,
camera, viewport, or pixels.

## 17. Validation

### 17.1 Validation phases

A Verifier executes these phases in order and does not publish partial results:

1. resource-limit preflight;
2. byte, UTF-8, and JSON lexical validation;
3. duplicate-member and canonical-byte validation;
4. format-version and schema validation;
5. section, cognition, and package digest recomputation;
6. closed-member, inventory, identifier, Workspace, ordering, and uniqueness
   validation;
7. Observation relationship/provenance grammar, provenance acyclicity, and
   cross-artifact reference closure;
8. deterministic Trace reconstruction;
9. deterministic Replay reconstruction;
10. deterministic Evolution reconstruction;
11. deterministic Comparative Reconstruction;
12. extension compatibility and prohibited-content validation; and
13. verification-section comparison.

The [compatibility-flow.mmd](diagrams/compatibility-flow.mmd) diagram shows the
compatibility branch; [conformance.md](conformance.md) defines required evidence.

### 17.2 Diagnostics

Diagnostics contain a stable `code`, RFC 6901 JSON Pointer `path`, and no
implementation-specific stack trace. Multiple diagnostics are ordered by
validation phase, then path, then code. Implementations may add localized
human-readable text outside the package; diagnostic code and path remain the
portable result.

Stable failure codes are:

`RESOURCE_LIMIT_EXCEEDED`, `INVALID_ENCODING`, `INVALID_JSON`,
`DUPLICATE_MEMBER`, `NON_CANONICAL`, `UNSUPPORTED_VERSION`,
`MISSING_REQUIRED_SECTION`, `UNKNOWN_CORE_MEMBER`, `SCHEMA_VIOLATION`,
`CHECKSUM_MISMATCH`, `WORKSPACE_MISMATCH`, `DUPLICATE_IDENTIFIER`,
`ORDER_VIOLATION`, `DANGLING_REFERENCE`, `INVALID_PROVENANCE`, `INVALID_TRACE`, `INVALID_REPLAY`,
`INVALID_EVOLUTION`, `INVALID_COMPARATIVE_RECONSTRUCTION`,
`UNSUPPORTED_CRITICAL_EXTENSION`, and `PROHIBITED_CONTENT`.

### 17.3 Conditional validity

- A Trace requires its exact included Observation.
- A Replay requires its exact included Trace and Observation.
- An Evolution requires its two included Observations in valid order.
- A Comparative Reconstruction requires both included Observations, both exact
  included Traces, and the included Evolution for that ordered pair.
- Every derived record must equal independent deterministic reconstruction.

Cryptographic integrity without semantic reconstruction is insufficient.

## 18. Import requirements

A conforming importer:

1. treats incoming bytes as untrusted;
2. stages parsing and all validation privately;
3. applies the phases in section 17;
4. preserves exact identifiers, authoritative order, unknown noncritical
   extensions, and semantic revisions;
5. neither repairs nor normalizes invalid content;
6. commits the complete package only after all mandatory checks pass; and
7. leaves existing state unchanged on failure.

Resource limits are Consumer policy, not MIP semantics. A Consumer may reject a
package before allocation when its declared or measured size exceeds policy,
but it reports `RESOURCE_LIMIT_EXCEEDED` and publishes no partial state.

## 19. Export requirements

A conforming exporter:

1. obtains one coherent, detached, successful source Observation set;
2. preserves source identifiers and authoritative semantic order;
3. emits no inferred, repaired, or fabricated cognitive content;
4. proves complete typed-reference closure;
5. recomputes every supplied derived artifact;
6. validates prohibited-content and extension rules;
7. calculates section, cognition, and package digests;
8. serializes exact RFC 8785 canonical bytes; and
9. publishes atomically only after complete verification.

An export failure leaves an existing destination unchanged and emits no partial
`.mip`. Exporters do not silently downgrade versions or discard extensions.

## 20. Versioning and compatibility

### 20.1 Independent versions

The specification version (`CCA-MIP-1.0`) and wire-format version (`1.0.0`)
are independent of MemoryOS, Producer, SDK, or application versions. Product
version strings in metadata do not select format behavior.

The wire format uses semantic versioning:

- **MAJOR** changes compatibility, core meaning, the core validation profile,
  canonicalization, or hashes;
- **MINOR** adds only optional, namespaced extension definitions; and
- **PATCH** clarifies defects without changing valid values, meaning, or
  canonical bytes.

Adding a required core field, changing an enum meaning, changing ordering, or
changing a digest rule requires a new MAJOR version.

Wire-format versions are stable numeric `MAJOR.MINOR.PATCH` values only.
Prerelease labels and build metadata are invalid because they would create
undefined compatibility ordering and noncanonical release identities.

### 20.2 Backward compatibility

A newer Consumer within the same major version **MUST** accept every valid
older minor and patch package. A newer Producer may export an older format only
when explicitly requested and only when the package is exactly representable;
it never silently drops data.

### 20.3 Forward compatibility

A Consumer rejects an unknown major version. Within a known major, a Consumer:

- validates all known core records as closed;
- rejects unknown top-level and core members;
- accepts and preserves unknown noncritical extension sections; and
- rejects unknown critical extensions atomically.

Minor versions do not add silent core fields. This rule makes forward
compatibility deterministic instead of dependent on permissive parsers.

The core `$schema` identifier remains
`urn:memoryos:mip:schema:1.0.0` throughout wire-format major version 1 because
minor versions can add only extension definitions, not core shape. The
`formatVersion` value, not a changed core schema identifier, identifies those
minor or patch publications.

### 20.4 Unknown sections

An unknown section is valid only as an entry in `extensions`. Its manifest
feature name and extension key must agree. A noncritical unknown section is
excluded from semantic interpretation but included in its section and package
digests. It must survive a read-write round-trip unchanged as a JSON value.

## 21. Security, privacy, and operational considerations

Packages may contain sensitive cognitive source material and provenance.
Producers should minimize package scope to the investigation being exchanged.
Consumers must apply appropriate access controls outside this format.

Checksums do not authenticate a producer. The core format contains no secrets,
credentials, encryption keys, executable content, or transport endpoints.
External transport and storage protections do not change canonical package
bytes.

## 24. Conformance

Conformance targets are Producer, Consumer, Verifier, and round-trip
implementations. Required evidence, golden vectors, negative vectors, and
claim language are defined in [conformance.md](conformance.md).

JSON Schema success alone is not a conformance claim. Semantic reconstruction,
reference closure, canonical bytes, hashes, compatibility, prohibited-content,
and atomic failure behavior are mandatory.
