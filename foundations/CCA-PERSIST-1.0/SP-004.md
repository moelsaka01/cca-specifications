# SP-004 Persistence Foundation Standard

## 1. Purpose and authority

This standard defines deterministic preservation and restoration of durable
Workspace state. It conforms to the frozen CCA architecture and does not
redefine constitutional concepts.

The Foundation preserves Workspace, Domains, Assets, Policies, metadata, and
Execution Context snapshots. Runtime implementation state is ephemeral and is
never preserved.

The terms **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** express
requirement strength. `MUST` and `MUST NOT` are normative.

Authority is ordered as follows:

```text
API-003-HPP -> API-003 -> SP-004 -> requirements -> IS-006
```

`api.hpp.md` is the sole declaration authority. `api.md` defines public
behavior. This standard defines architecture; the requirement registry and
implementation specification add traceability and private constraints only.

## 2. Scope

CCA-PERSIST-1.0 defines `PersistencePackage`, `PersistenceMetadata`,
`PersistenceResult`, `PersistenceEngine`, `PersistenceFormat`, and
`ExecutionContextSnapshot`. `PersistenceEngine` is the public service.

The Foundation defines package ownership, validation, deterministic ordering,
save and load semantics, result diagnostics, and exclusion of Runtime
implementation state.

## 3. Architectural position

Persistence preserves Workspace state across disposable Runtime lifetimes. It
does not become a Domain, Service, Policy, Provider, or Contract. Providers may
provide external preservation infrastructure, but Providers do not define
Persistence architecture.

Persistence depends on public Representation and Process contracts only. It
does not cause Runtime to depend upward on Persistence.

## 4. Preserved state

A package contains one complete Workspace representation, ordered Policy
identifiers, its metadata, persisted ProcessDefinitions, the selected
canonical format identifier, and zero or more Execution Context snapshots.
Entity, relationship, property, Policy, and metadata ordering is retained.
Runtime lifecycle, registries, providers, threads, diagnostics sinks, and other
implementation state are excluded.

## 5. Determinism and integrity

Equivalent semantic input produces equivalent package content, validation
outcomes, diagnostics, and restoration order. Validation is side-effect free.
Save and load either produce a complete valid result or report failure without
partially exposing a package. A package is immutable after successful creation.

## 6. Lifecycle

```text
Workspace state + Policies + ProcessDefinitions -> save -> immutable package
immutable package -> validate -> load -> independently restored package state
```

Loading does not start Runtime or Services. A caller may subsequently provide
the restored Workspace to a disposable Runtime through the existing public
composition boundary.

Save creates an owned package from caller-provided state. Load consumes an
already available package at the Persistence boundary and returns an
independent restored package. Neither operation selects or mandates a Provider,
external medium, or representation mechanism.

## 7. Ownership and lifetime

Persistence owns package contents by value. Source Workspace state remains
caller-owned and is observed without mutation. Results own their diagnostics
and, on success, the package they return. Context snapshots own copied trace
and state data.

## 8. Out of scope

This standard does not define databases, cloud providers, serialization
formats, compression, encryption, networking, distributed persistence,
replication, synchronization, or storage engines. Those concerns belong to
Providers and are not public Persistence architecture.
